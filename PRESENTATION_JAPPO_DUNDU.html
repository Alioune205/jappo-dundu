Ce qu’on présente, comment l’installer, comment le montrer

Ce document accompagne la branche version-presentation. Il explique la partie du projet que nous présentons, comment chaque membre de l’équipe l’installe pour la tester, et le déroulé exact de la soutenance.

1. L’idée en une phrase

Au Sénégal, quand une urgence arrive, trois informations manquent au même moment : où trouver du sang compatible, quel hôpital a un lit libre et quelle ambulance est la plus proche. Jappo Dundu réunit ces trois informations sur une seule plateforme, en temps réel.

Message à retenir pour le jury : on ne remplace pas les hôpitaux, le CNTS ou le SAMU. On les connecte, pour qu’aucune minute ne soit perdue à téléphoner pour chercher une information.

La plateforme a trois parties :

Backend (API)

Django. Stocke les données, calcule les distances, envoie les alertes en temps réel.

Site web

React. Utilisé par les hôpitaux, le CNTS, la régulation SAMU et l’administrateur.

Application mobile

Expo / React Native. Utilisée par les donneurs, les citoyens (SOS) et les ambulanciers.

2. Ce qui est présenté : le cœur du sujet

Cette version n’affiche que l’essentiel. Trois parcours, plus le SOS et le tableau de bord.

Module 1 Banque de sang

Le CNTS / l’hôpital crée une demande→les donneurs compatibles et proches sont alertés→un donneur accepte→le don est confirmé

Le système choisit les donneurs selon le groupe sanguin compatible, la distance et l’éligibilité (délai depuis le dernier don).

Module 2 Lits d’hôpital

L’hôpital met à jour ses lits par service→admissions et sorties→réservation d’un lit→la carte nationale se met à jour

Chaque service (urgences, réanimation, maternité…) affiche ses lits libres. Le tableau de bord voit immédiatement les hôpitaux saturés.

Module 3 Ambulances (SAMU)

La régulation crée une mission→l’ambulance libre la plus proche est affectée→l’hôpital de destination reçoit une préalerte→il accepte ou refuse le patient→l’ambulancier suit la mission sur son téléphone

Transversal SOS citoyen et tableau de bord national

Depuis l’application, un citoyen envoie un SOS avec sa position ; la régulation le reçoit et peut en faire une mission. Le tableau de bord national montre sur une carte les lits, les demandes de sang et les ambulances, mis à jour en direct.

3. Ce qui est masqué (mais pas supprimé)

Le projet complet contient beaucoup plus de fonctions. Pour une présentation claire, elles sont cachées derrière un interrupteur. Le code est toujours là et les tests les vérifient toujours.

ModuleFonctions masquées
SangStocks de poches, commandes entre banques, collectes mobiles, choix du produit (plasma, plaquettes), groupes rares, relance par vagues, suivi « je suis en route »
LitsBadge de fraîcheur des données, sorties prévues, alerte de saturation, plateau technique, transferts
SAMUQuestionnaire de tri, lien de localisation par SMS, fiche de l’appelant, bilan médical, contrôle du véhicule, prévision de la demande
SupervisionIndicateurs, rapport hebdomadaire, salle de crise, alertes critiques, double authentification, journal d’audit, interopérabilité (FHIR, DHIS2), demandes d’adhésion, recommandations de l’IA
MobilePartage, auto-évaluation avant le don, carte d’impact, parrainage, fiche d’urgence, contrôle de prise de poste, bilan

Pour tout réafficher (si le jury demande « que pourrait-on ajouter ? ») :

  • Site web : ajouter VITE_FULL_FEATURES=true dans frontend/.env.local, puis relancer npm run dev.
  • Mobile : ajouter EXPO_PUBLIC_FULL_FEATURES=true dans mobile/.env, puis relancer Expo.
Conseil : ne réactivez pas tout pendant la démonstration. Mentionnez ces fonctions dans la partie « perspectives » ; c’est plus convaincant qu’un écran surchargé.

4. Installation pour tester

Prérequis : Git, Python 3.11 ou plus, Node.js 20 ou plus. Pas besoin de PostgreSQL : en local on utilise SQLite. Les commandes sont pour Windows (PowerShell).

Étape 1 — Récupérer la branche

git clone -b version-presentation https://github.com/Alioune205/jappo-dundu.git
cd jappo-dundu

Si vous avez déjà le dépôt :

git fetch origin
git checkout version-presentation
git pull

Étape 2 — Backend (terminal n°1)

cd backend
python -m venv venv
.\venv\Scripts\activate
pip install -r requirements.txt
copy .env.example .env

Ouvrez backend\.env et modifiez ces lignes :

DEBUG=True
DB_ENGINE=django.db.backends.sqlite3
REDIS_URL=

Puis créez la base, chargez les données de démonstration et lancez le serveur :

python manage.py migrate
python seed_demo_data.py
python manage.py runserver 0.0.0.0:8000

L’API répond sur http://127.0.0.1:8000. Laissez ce terminal ouvert.

Étape 3 — Site web (terminal n°2)

cd frontend
npm install
npm run dev

Ouvrez l’adresse affichée (en général http://localhost:3000).

Étape 4 — Application mobile (terminal n°3)

cd mobile
npm install
copy .env.example .env

Dans mobile\.env, mettez l’adresse du backend :

  • pour tester dans le navigateur : EXPO_PUBLIC_API_URL=http://127.0.0.1:8000 puis npx expo start --web ;
  • pour tester sur un téléphone (même Wi-Fi que le PC) : l’IP du PC, par exemple EXPO_PUBLIC_API_URL=http://192.168.1.20:8000 (commande ipconfig pour la trouver), puis npx expo start et scannez le QR code avec Expo Go.

Étape 5 — Vérifier que tout fonctionne (facultatif)

cd backend   →  python manage.py test --parallel 1
cd frontend  →  npm test
cd mobile    →  npm test
Problèmes fréquents :
  • « Port déjà utilisé » : un autre serveur tourne déjà. Fermez-le ou changez le port (runserver 0.0.0.0:8002, puis VITE_DEV_BACKEND_URL=http://127.0.0.1:8002 dans frontend\.env.local).
  • Le téléphone ne se connecte pas : vérifiez l’IP, le même Wi-Fi, et que le backend tourne bien avec 0.0.0.0.
  • « activate » refusé par PowerShell : lancez Set-ExecutionPolicy -Scope CurrentUser RemoteSigned une fois.

7. Déroulé de la présentation (≈ 20 minutes)

Répartissez les étapes entre les membres : chacun présente le module qu’il connaît le mieux et répond aux questions dessus.

  1. 2 minLe problème. Une situation concrète : un accidenté arrive, il faut du sang O−, un lit en réanimation et une ambulance. Aujourd’hui : des appels téléphoniques, un à un. Donner un chiffre de contexte si vous en avez un sourcé.
  2. 2 minLa solution et l’architecture. Une diapositive : backend, site web, mobile ; qui utilise quoi (tableau des profils de la section 5).
  3. 4 minDémo 1 — Sang. Connecté en cnts.dakar, créer une demande O+. Montrer le téléphone de awa.ndiaye qui reçoit l’alerte, accepter, puis confirmer le don sur le web. Phrase clé : « le système ne prévient que les donneurs compatibles, proches et éligibles ».
  4. 3 minDémo 2 — Lits. Connecté en dr.diop, modifier les lits des urgences, enregistrer une admission. Basculer sur le tableau de bord : la carte a changé sans recharger la page.
  5. 4 minDémo 3 — SAMU. Connecté en samu.regulation, créer une mission. Montrer l’ambulance la plus proche affectée automatiquement. Sur le compte dr.diop, accepter la préalerte. Sur le téléphone de samu.driver, faire avancer la mission.
  6. 2 minSOS citoyen. Depuis le mobile, envoyer un SOS ; il apparaît côté régulation.
  7. 1 minTableau de bord national. Vue d’ensemble pour le ministère / l’administrateur.
  8. 2 minBilan et perspectives. Ce qui marche, ce qui reste à valider sur le terrain (avec le CNTS et le SAMU), et les fonctions déjà prototypées (section 3) : stocks, tri médical, interopérabilité.
Plan B : enregistrez une vidéo de chaque démo la veille. Si le Wi-Fi ou un serveur tombe, passez la vidéo sans perdre de temps. Préparez aussi des captures d’écran dans les diapositives.
Honnêteté : dites clairement que la plateforme n’a pas encore été testée avec de vrais utilisateurs et qu’elle n’est pas déployée en production. Si des outils d’IA ont aidé au développement, mentionnez-le comme demandé par l’école. Un jury apprécie la transparence.

8. Questions probables du jury

QuestionPiste de réponse
Comment choisissez-vous les donneurs à alerter ?Compatibilité du groupe, distance au point de collecte, délai minimal depuis le dernier don, disponibilité déclarée.
Comment trouvez-vous l’ambulance la plus proche ?Position des ambulances libres et calcul de distance géographique (GeoDjango / PostGIS en production).
Comment le temps réel fonctionne-t-il ?WebSockets (Django Channels) pour le web, notifications push Expo pour le mobile.
Et la sécurité des données de santé ?Chaque profil ne voit que son périmètre (son hôpital, sa région), authentification par jeton, données minimales dans les alertes.
Que se passe-t-il si un hôpital ne met pas ses lits à jour ?C’est la principale limite : la qualité dépend des saisies. Le projet complet prévoit des rappels automatiques et un indicateur de fraîcheur.
Comment l’avez-vous testé ?Tests automatisés sur le backend, le web et le mobile ; validation terrain encore à faire.
Qui a fait quoi ?Chaque membre présente sa partie (backend, web, mobile, données / IA).

9. Check-list de la veille

  • Tout le monde est sur la branche version-presentation à jour (git pull).
  • La base est remise à zéro avec les données de démo : supprimer backend\db.sqlite3, puis migrate et python seed_demo_data.py.
  • Les trois serveurs démarrent sur le PC de présentation.
  • Le téléphone de démo est connecté au même réseau et l’application est ouverte sur le bon compte.
  • Les comptes sont déjà connectés dans des onglets séparés (gain de temps).
  • Les vidéos de secours sont sur le PC et sur une clé USB.
  • Une répétition complète chronométrée a été faite (moins de 20 minutes).
  • Chaque membre sait répondre aux questions de son module.
